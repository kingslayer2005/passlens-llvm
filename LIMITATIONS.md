# Limitations

While this research provides an interpretable framework for understanding ML-guided compiler optimization decisions using SHAP, it is subject to several structural and methodological limitations.

## 1. Code Size Objective vs. Execution Time
Our pipeline strictly evaluates "beneficial" passes as those that reduce the **static instruction count** (code size). We do not measure runtime performance (execution time) on real hardware. Reducing static instruction count often correlates with smaller binary sizes (like `-Oz`), but it is not a reliable proxy for execution speed (`-O3`), as loop unrolling or vectorization intentionally increase instruction count to improve latency or throughput.

## 2. Single-Pass Marginal Effects and Phase Ordering
Our labels are generated by evaluating the marginal effect of applying a single pass $P$ after a random prefix of passes. 
- This partly captures phase-ordering effects (how earlier passes condition the IR for later passes), but it does not fully model the combinatorial explosion of full sequence interactions.
- A pass might be detrimental locally but open up significant optimization opportunities for a subsequent pass. Our greedy, immediate-reward approach fails to capture delayed-reward optimizations.

## 3. Limited and Homogeneous Benchmark Suites
The models are trained exclusively on PolyBench/C and MiBench. 
- PolyBench is heavily biased toward dense numerical loop nests and stencil computations.
- MiBench targets embedded systems.
- The learned heuristics and SHAP feature importance may overfit to the idioms of these specific suites and might not generalize to object-oriented code (C++), highly concurrent systems (Rust/Go), or different domains like web servers or compilers.

## 4. Static Feature Limitations
Our feature set relies entirely on 40 static Autophase-style structural and opcode density features (e.g., `add` instruction densities, CFG edge counts).
- We do not capture dynamic behaviors, such as memory access patterns, branch probabilities, or cache miss rates.
- Graph-level properties (like data dependencies and dominator trees) are only weakly approximated by predecessor/successor distributions.
- Advanced representation learning methods (like IR2Vec, ProGraML) could capture much richer semantic contexts than our flat, handcrafted feature vectors, though at the cost of direct interpretability.

## 5. Intraprocedural Scope
Our dataset extracts single functions into isolated modules (`llvm-extract`). As a result, we only evaluate **intraprocedural** passes. We entirely miss cross-module optimizations, Link Time Optimization (LTO), and interprocedural analysis (IPA/IPO) such as inlining, which are critical components of modern `-O2` and `-O3` pipelines.

## 6. Compile Coverage and Dataset Balance
- Only 496 of 1118 benchmark source files compile outside their own build
  system (PolyBench 30 of 31, MiBench 466 of 1087). Most failures need a
  header that the benchmark's build generates (`arch.h` for ghostscript,
  `config.h`, `jconfig.h`) or target another platform (Windows, X11, GTK).
  Within a program, the sampled functions therefore come from its more
  self-contained files (ghostscript: 44 of 488 files).
- 107 of the compiled MiBench files needed a legacy C dialect
  (`-std=gnu89` with implicit declarations allowed). The mode used is
  recorded per function (`compile_mode`).
- The dataset is unbalanced across groups: the 8 largest programs hold 77 %
  of the 2953 samples, while each PolyBench kernel contributes 3-4
  functions. Results must be reported with programs as the resampling unit.
- A function's states are correlated with each other; they always share a
  cross-validation group.

## 7. Loop Canonicalization
Loop passes in LLVM's new pass manager run LoopSimplify and LCSSA first. The
dataset records the size after this step separately (`inst_control`), but
the canonical form is still part of what the pass sees and produces.

## 8. Statistics
- Folds of a cross-validation share training data, and the three repeats
  reuse the same samples, so the fold-level Wilcoxon test is optimistic. A
  target counts as predictable only if a bootstrap over whole programs
  agrees.
- Several kept targets are rare (positive rate 6-12 %), and their positives
  can sit in a few programs. Their estimates are noisy even when a test
  passes.
- Heuristic lists are short (one to three features per pass). A single pass
  cannot reach significance on its own; the pooled test carries the
  evidence, and pairs of one pass (for example `fired` and `beneficial`)
  are not independent.

## 9. What SHAP Agreement Does and Does Not Mean
- SHAP describes which inputs the model relies on. It is not a causal
  statement about the pass.
- The cost-model features are proxies. LLVM's loop-rotate threshold applies
  to the header of each loop, the unroll threshold to the unrolled size
  (body size times trip count), and the jump-threading threshold to the
  block being duplicated; the dataset has one number per function.
- Agreement with `heuristics.yaml` shows that the model is consistent with
  what a pass operates on. It does not show that the model rediscovered
  LLVM's logic, and entries marked `verified: false` have not been checked
  against the source.
- Features that move together (Spearman |rho| above 0.8) are scored as one
  cluster, because SHAP splits credit between them. `ret_density` falls in
  the same cluster as `log_inst_count` and is treated as a size feature.

## 10. Sequence Evaluation
- The model-guided selector is greedy and uses only the `beneficial`
  models. It is a check that the per-pass models are usable together, not a
  competitor to `-Oz`, which also runs interprocedural and many more passes.
- `-O2` optimizes for speed and can increase the instruction count.
